# Connected cloud and post flows

The camera/map UI now connects creation and creator-only deletion of clouds, author-only deletion of posts, public authors, and lifecycle reconciliation. Canonical v1 receives two additive optional fields: `Message.author` references the existing public `User`, and `CreateCloudRequest.datasetId` selects an already provisioned dataset. Omitted dataset keeps the configured server default. Live/replay clocks remain isolated by dataset. Existing consumers and fixtures remain valid; generated frontend bindings must be regenerated from the schema.

`GET /api/v1/messages/:id` returns the current public message, including its current cloud and anchor after transport. Held, expired or unavailable content returns 410; removed/unknown IDs return 404. Clients revalidate locally created or loaded posts and remove unavailable entries; absence from three previews alone does not imply deletion. Late responses from previous accounts, queries or mutations must not restore stale data.

`GET /api/v1/messages?id=one&id=two` revalidates up to 50 IDs in one snapshot and returns current visible `Message` objects in a data envelope. Missing/unavailable IDs are omitted; the client must only remove IDs it actually queried. Polling preserves main's shared `DISCOVERY_RADIUS_M` policy (50 km), including cached-post and loaded-row filtering. The existing worker coverage expansion and recovery logic is unchanged.

Create message/cloud requests may send `Idempotency-Key` (1–128 URL-safe characters). Receipts are scoped to the authenticated user for 24 hours, bound to the path and canonical request digest, and committed atomically with the object. Matching retries return the same object ID with its current visible state; different payload/path returns 409. Expired/deleted/held content is not recreated or returned from a cached body. Receipts retain only digests and object IDs and expire explicitly as well as through TTL. Requests without the header remain supported. Votes retain desired-state semantics.

The browser keeps a key for an unchanged draft through network/server errors and rotates it after a definite rejected/edit/new request. Creation and deletion never bypass Clerk. Creator/author controls use the verified current Clerk user ID; the server remains authoritative. Public authors are projected through an explicit id/name/avatar allowlist; no email or location history is exposed.

An ambiguous message retry keeps the original complete request, including `expectedCloudVersion`, even if a sky poll advances that version or the user must sign in again. A definitive stale-cloud conflict clears the attempt so the user can re-place against the refreshed cloud. An accepted but held/deleted original keeps its key and displays that status instead of silently creating another post. Otherwise normal tracking could make the same retry look like a new post. These keys last for the mounted draft; a cancelled/new draft is a new intent.

Integration baseline: main `328c242`, including shared 50 km phone discovery and worker coverage/recovery changes. Reapplication overlaps in sky polling and the cloud sheet were resolved without altering production worker logic. The two live-supervisor tests replace only their own module's sleep binding, avoiding interference with MongoDB background threads in the combined suite. Verification: 107 backend/contract/worker tests and 65 frontend tests pass; Ruff, mypy, TypeScript, ESLint, fixture/schema checks and production web build pass. Real phone/Clerk acceptance remains separate.
